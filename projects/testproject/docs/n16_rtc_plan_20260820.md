# N1.6 RTC Plan: Continuous Motion via Pipelined Requests

Date: 2026-08-20
Status: PLAN — approved for implementation after review
Prerequisite reading: `n16_jpeg_payload_port_plan_20260813.md` (the transport
this builds on), `pi05_rtc_first_live_sessions_20260801.md` (the other
pipeline's RTC lessons, incorporated below).

## 0. The problem, measured — not assumed

From the 20-run A/B campaign (4,400+ decision cycles, all traced):

```text
sequential loop today:   obs -> request -> WAIT 564 ms frozen -> move 267 ms -> repeat
cycle time               845 ms measured median (559 rtt + 267 motion + ~15 overhead)
duty cycle               31% moving / 69% frozen
carry tempo              demos: 2-3 s   hardware: 30-90 s
decisions per carry      demos: ~2-3    hardware: 30-100
```

Why this matters is no longer speculative. The Brain A over-carry
investigation (2026-08-20) established the failure mechanism:

1. The policy has NO velocity input. A snapshot at pan +50 while sweeping
   and a snapshot at pan +50 while settling are identical to it. Whether a
   cycle samples "settle and release" or "keep swinging" is a dice roll on
   near-identical inputs (poses and frames at the release-zone crossing were
   indistinguishable between the 4 completions and 6 failures).
2. Every extra decision cycle during the carry is an extra pull on those
   dice. Past pan ~+65 the scene leaves the trained release distribution and
   "open" stops being sampled at all — a one-way door (0 releases in 600+
   post-zone cycles across the 6 failures; all pinned at pan +116.5, wrist
   then drifting to its own -102.5 limit).
3. Off-distribution drift compounds with TIME spent in states no demo
   contains (Brain B's backward-wrist collapse: starts in-range, walks out
   over a 60-90 s carry).

RTC attacks the common root: it returns the rollout to demo-like tempo,
cutting decisions-per-carry ~10x and shrinking the drift window by the same
factor. It is the highest-leverage software fix available, and it does not
touch the model.

## 1. Design: pipelined double-buffer ("RTC-lite"), switch at chunk boundary

A lucky coincidence makes the simple design nearly optimal here:

```text
chunk duration    16 actions @ 30 Hz = 533 ms
round trip        median 564 ms  (p95 610)
```

The inference delay almost exactly equals one chunk of motion. So:

```text
t=0        capture obs A, send request A            (arm idle - startup only)
t=564      chunk A arrives. START EXECUTING A (all 16 actions).
           simultaneously: capture obs B, send request B
t=1097     A exhausted (533 ms). chunk B arrives ~t=1128.
           hold last position ~31 ms (median starvation), switch to B,
           capture obs C, send request C
...continuous from here on
```

- Steady-state duty cycle ~533/564 = 94% (vs 31%).
- Exactly ONE request in flight at a time — no server change, the ZMQ
  REQ/REP pattern and the JPEG transport stay untouched.
- Chunks are consumed WHOLE and switched at natural boundaries. The pi0.5
  RTC sessions showed seams are most dangerous mid-chunk during grip
  transitions (execution_horizon 10 << inference delay -> "chunk switches
  during the grip->lift transition still wavered the grip"; fixed at h=35
  covering the delay). Our boundary-switch design has the same property as
  their fix: the executing window covers the inference delay.

### Costs, priced honestly

1. Steps 9-16 of every chunk now execute. Measured offline accuracy:
   step 1 = 1.23 deg, step 8 = 2.26, step 16 = 3.39 mean error. We trade
   per-step accuracy for tempo, ON EVIDENCE: the 4 successful releases all
   happened in runs whose zone-crossing behaviour the policy sampled
   correctly; per-step precision was never the failure mode. The failure
   mode was too many decisions.
2. Observation staleness at the tail: action 16 executes ~1.1 s after its
   obs (today: unused). Bounded by the same re-plan-every-chunk rhythm.
3. Fresh-look cadence stays ~1.1 s per look (one look per chunk) vs
   today's 0.85 s. Slightly fewer looks per second — but each look now
   governs continuous motion, which is what the demos looked like.

### Alternative considered and deferred: blended RTC (pi-style inpainting)

Cross-fading overlapping chunks only matters when the new chunk arrives
BEFORE the old one is exhausted (rtt < chunk duration). Ours arrives after
(564 > 533), so there is no overlap to blend at median rtt. On fast-rtt
outliers (<533 ms) v1 simply switches at the boundary anyway (the new chunk
waits a few ticks — harmless). Blending adds complexity for a case our
network doesn't produce; revisit only if a future faster link changes the
regime.

## 2. Client changes (the whole diff lives in `n16_realarm_client.py`)

1. `--rtc=true|false` flag. `false` = today's sequential path, byte-identical
   behaviour. Rollback is a flag flip.
2. A single background thread owns the PolicyClient socket:
   loop { take latest obs snapshot -> get_action -> put chunk on a
   1-slot queue }. Main thread never blocks on the network.
3. Main thread at 30 Hz: pop chunk if available (else continue current);
   execute actions in order; on exhaustion with no new chunk, HOLD last
   commanded position; if starved > 60 ticks (2 s — covers the observed
   4.2 s rtt outlier only via abort), freeze and exit with a clear error.
4. Obs capture moves to the moment the background thread becomes free
   (freshest possible input), including the wrist-proxy fetch.
5. Trace additions per chunk: `chunk_age_ms` (obs capture -> first action
   executed), `starved_ticks`, `switch_tick`, `rtc: true`. Everything the
   analysis scripts already read stays unchanged.

Estimated size: ~100 lines. No server, camera, instruction, or model change.

## 3. Validation gates — in order, no skipping

```text
G0  dry-run (no arm): --rtc=true --dry_run=true against the live server.
    PASS: >=20 chunks, zero deadlocks, measured duty >=90%, starvation
    median <=2 ticks, clean ctrl-C.
G1  arm, motion only (NO orange on table): one 60 s run.
    PASS: continuous motion visible, no oscillation/seam jerks at chunk
    boundaries (max per-tick joint step comparable to sequential runs),
    trace shows duty >=85%.
G2  arm, live task, 3 runs (operator present, orange mid-table):
    COMPARE against the 10-run sequential baseline:
      - grasp-to-zone time        (baseline 30-60 s; expect <10 s)
      - decisions during carry    (baseline 30-100; expect <8)
      - over-carry rate           (baseline 6/10)
      - completions
    3 runs decide nothing statistically - they gate whether a full 10-run
    scored set is worth the operator's time.
```

## 4. Risks

```text
R1 seam jerks at chunk switch (pi0.5's plague)   boundary-switch design +
                                                 G1 max-step check
R2 rtt spike starves the queue                   hold-position + 2 s abort;
                                                 p95 610 ms = 2-3 held ticks
R3 stale tail sends arm somewhere wrong          bounded: 533 ms of pre-
                                                 committed motion, same order
                                                 as demos' own chunk scale
R4 thread races on socket/obs                    single owner thread, 1-slot
                                                 queue, no shared mutation
R5 faster carries change what the wrist camera   this is the POINT - motion
   sees (blur closer to demo levels)             returns toward training data
```

## 5. What success unlocks

Brain A grasps 10/10 and fails only by not stopping. If demo-tempo carries
restore demo-like release behaviour, completion rate should move sharply
toward the sim benchmark (86%). If over-carries persist even at 2-3
decisions per carry, the remaining gap is data, not tempo — and the plate
demos (next plan) carry the load. Either way the answer is clean.

## 6. Out of scope

The release guard (explicitly deferred by operator decision, 2026-08-20),
new demos/fine-tuning, server changes, camera changes, Brain B.
